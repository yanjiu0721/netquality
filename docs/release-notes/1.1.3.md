# 网络质量探测 1.1.3

版本名 `1.1.3`，构建号 `6`。应用标识和签名没有改，新的安装包会覆盖原来的程序，不用先卸载。

## 自更新

设置里有「自动检查更新」，默认打开。启动时会检查，设置里也可以点「检查更新」。先问 GitHub：

`https://api.github.com/repos/yanjiu0721/netquality/releases/latest`

连不上再问言灸的 Git：

`https://git.yanjiu.ltd/api/v1/repos/YanJiu/netquality/releases/latest`

有更新而且自动更新开着时，会下载当前系统对应的包。Windows、Linux amd64、Linux arm64，以及 Android 的 arm64-v8a、armeabi-v7a、x86_64 各有一个包。发布里如果有 SHA256SUMS，会先核对，对不上就停止。没有校验和文件时仍会安装，并在界面上说明。

关掉自动更新以后，启动时不检查，也不会自动下载。手动「检查更新」仍然可用，看到新版本后再点「下载并安装」。

Windows 和 Linux 把新文件写回当前安装目录，不另起一个程序。设置、节点、口令和探测历史放在应用数据目录，不在安装目录里，覆盖安装不会把它们清掉。Windows 上正在运行的程序文件不能当场替换，会等进程退出后再复制并重新打开。

Android 必须经过系统的安装确认，程序不能跳过这一步。界面上会写明。

1.1.2 没有更新器。从 1.1.2 升到 1.1.3 仍然要自己安装。自更新从 1.1.3 这一版才开始。

没有真正的新版本时，可以用环境变量试这个流程。`NQ_UPDATE_GITHUB_API` 和 `NQ_UPDATE_GITEA_API` 指向一份和上面接口同样格式的 JSON。

安装包名称：

- `netquality-client-1.1.3-windows-amd64.zip`
- `netquality-client-1.1.3-linux-amd64.tar.gz`
- `netquality-client-1.1.3-linux-arm64.tar.gz`
- `netquality-client-1.1.3-android-arm64-v8a.apk`
- `netquality-client-1.1.3-android-armeabi-v7a.apk`
- `netquality-client-1.1.3-android-x86_64.apk`

名字里带 server 或 reflector 的包不会被客户端选中。

## 最近目标

点「开始探测」之后，会记下主机或 IP、端口和探测类型。HTTP 还会记下 URL 和方法。目标框旁边的按钮列出这些记录，点一条会填回表单。每一条可以删除，也可以全部清除。最多保留 40 条。相同的目标只留最新的一条，并放到最上面。

这份列表只在本机。它不保存节点口令、中心口令、Cookie 或请求体。它和菜单里的「更新历史」不是同一页。

## IPv4 / IPv6

设置里两个开关，默认都开着。解析完成以后，只向打开的地址族发包。只开一个就只用那一个。两个都关掉时不会开始，并说明原因。目标本身就是已经关掉的那种地址时，也不会开始。

远程任务会带上 `allowIPv4` 和 `allowIPv6`。1.1.2 的节点不认识这个开关。两个都开着时，它仍按原来的方式探测。关掉其中一个时，客户端会先看 `/v1/info` 里有没有 `ipFamily: true`，没有就提示需要 1.1.3，而不是让旧节点继续用另一个地址族。结果里的实际地址和地址族，仍是这一次真正用到的那个。

## HTTP

新增探测类型「HTTP」。目标可以是主机名，也可以是 `https://example.com/path` 这样的完整地址。没写端口时，https 用 443，http 用 80。切换探测类型时，端口仍按原来的规则：只有当前端口是空的，或仍是上一种类型的默认端口，才会跟着换。离开 HTTP 时，80 和 443 都算默认端口。

协议默认是 HTTP/2，不行再降到 HTTP/1.1。也可以强制 HTTP/1.1、HTTP/2 或 HTTP/3。强制的版本不被支持就失败，不会悄悄换成另一种。明文连接上强制 HTTP/2 或 HTTP/3 也会失败，因为那两种需要 HTTPS。

指定解析的写法和 curl `--resolve` 一样：Host 和 SNI 仍用目标网址，TCP 或 QUIC 改连填写的 IPv4 或另一个主机名。这不是把某个地址当成 DNS 服务器。

方法可以是 GET 或 POST。POST 可以带请求体。Referer、User-Agent、Cookies 都是可选的。最大跳转次数默认 5。最终状态码是最后一跳的，结果里会列出跳转链。301、302、303 会改成 GET 并丢掉正文；307、308 保持原来的方法和正文。

每一次记下 DNS、连接、TLS、首字节、总时间、状态码、最终 URL，以及实际用到的 HTTP 版本。总时间用作曲线上的延迟。已经收到 HTTP 响应就算成功，4xx 和 5xx 只显示状态码，不叫丢包。

本机和远程节点用的是同一个 Go 引擎，里面包含 HTTP/3。桌面端把 `netquality-reflector` 放在程序旁边，或设置 `NQ_PROBE_HELPER`。找不到时，本机 HTTP 会说明缺引擎，远程 HTTP 不受影响。Android 如果系统不允许从应用目录启动这个程序，本机 HTTP 同样会说明，而不是改用另一套实现。

1.1.2 的节点没有 `http` 这个类型。客户端看到 `/v1/info` 里没有它，会提示节点需要升级。

## 中心

同一个 Go 程序可以当中心。配置放在一个目录里，示例是 `server/example-center`，口令都是占位。

```bash
./netquality-reflector -mode center -center-dir example-center -control-addr 127.0.0.1:8443
```

客户端新增「一键添加服务器」。填写中心地址、账号和口令。中心要求密码、手里还没有口令时，可以填账号和密码，登录后拿到的是一条会话口令，不是原来的长期口令。确认一次，会加入这个口令能用的全部服务器。一个客户端可以保存多个中心口令。展开后能看到名称；非保密节点还会看到地址。点刷新会跟上中心新增和删除的服务器。原来的「管理节点」还在，手动添加的节点和中心下发的节点可以同时存在。中心分配的名称不能在客户端里改。

保密节点的地址、IP 不会出现在客户端界面和本地保存的数据里，只保留中心分配的名称。对它的探测由中心转发到节点。中心不会把节点的长期口令交给客户端。非保密节点拿到的是大约 15 分钟的短期凭证，客户端用它直接连接。

中心的控制接口和节点一样，给别人用时要走 HTTPS。目录里只保存哈希。生成方式：

```bash
printf '%s' '换成你自己的口令' | ./netquality-reflector -hash-secret
```

1.1.2 的节点仍可以手动添加。要当中心，或当中心下发的节点，需要 1.1.3 的服务端。节点上要配置和中心相同的 `NQ_CENTER_KEY`，以及和服务器文件 `id` 相同的 `NQ_SERVER_ID`。systemd 和防火墙的例子在 `docs/server-linux.md`。
